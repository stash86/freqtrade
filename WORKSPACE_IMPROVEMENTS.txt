Scope and evidence
------------------
Broad, targeted review of runtime/strategy/data/exchange code, persistence,
RPC/REST/WebSocket/client code, pairlists/protections, custom hyperopt losses,
configuration, Docker/Compose, scripts, packaging, and CI. This is a list of
actionable findings and candidates from the review, not proof that every possible
improvement has been found.

Observed baseline: pyproject.toml already had one user modification, changing the
Pyright Python version from 3.11 to 3.13. That modification was preserved.

Checks performed:
- Parsed 497 tracked Python files outside named FreqAI/orderflow files: no syntax
  errors. Two invalid-escape SyntaxWarnings occurred in scripts/frogtrade9000.py.
- Parsed 155 tracked non-FreqAI user configuration JSON files with Freqtrade's
  comment/trailing-comma support: no syntax errors. Values were not included here.
- Current docker-compose.yml passes Compose's quiet configuration check.
  docker-compose.yml.example fails YAML parsing.
- Inspected shell scripts pass bash -n; scripts were not executed operationally.
- Ran small offline reproductions using synthetic data, in-memory SQLite,
  temporary directories, and mocked exchange/network boundaries.
- Compared ordered string deduplication on 1,000 generated cases and measured a
  local microbenchmark. This is not a measured improvement to overall bot speed.
- Existing tests were inspected but not changed or run. Each validation entry
  below describes checks required before a future implementation is accepted.
- No live trading, deployment, package installation, database migration, database
  commit change, or external notification was performed. Data/log/result binaries
  were not exhaustively inspected; no dependency-advisory audit was performed.

Constraints for any later implementation:
- Exclude FreqAI/orderflow optimization work, schema migrations, and changes to
  database commit behavior. Preserve FtPrecise calculations.
- Preserve every public API field/dataframe column, including balance history.
- Low/medium-risk optimizations must pass unchanged existing tests. Add meaningful
  regression coverage for demonstrated bugs where appropriate; do not weaken or
  rewrite existing tests to make an optimization pass.
- Search existing helpers first; suggested reuse is identified where it fits.
- Preserve eager order history for retained/callback-bound trades and the
  analyzed-dataframe copy before RPC conversion mutates its data.

Reading the list
----------------
P1: address before using the affected workflow/feature.
P2: normal correctness/reliability/security work.
P3: optional maintenance, compatibility design, or profiling work.
Risk estimates describe implementing the suggestion, not the severity of its bug.
"Reproduced" means a controlled local case demonstrated the behavior.
"Source-confirmed" means the code path is visible, without a live reproduction.
"Candidate" means more measurement, integration checks, or policy decisions are
needed. Conditions are stated explicitly; these are not claims of live incidents.

Suggested starting order: A01, A02, A03, R01, R03, R13, D01-D05. Performance
candidates should follow the correctness fixes and workload measurement.
